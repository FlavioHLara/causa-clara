1Convenções adotadas

Os diagramas de caso de uso foram divididos por grupo de atores para caber de forma legível. No diagrama do Gestor, a ligação do ator chega à borda do pacote: isso significa que o ator acessa todos os casos de uso daquele pacote. Ao refazer na ferramenta, expanda em uma linha por caso de uso — o código PlantUML da seção 4 já traz todas as associações expandidas.

A generalização entre atores segue uma regra única: ela só aparece quando as capacidades de um ator são um superconjunto das do outro. É o caso de Apoiador sobre Visitante e de Gestor Dono sobre Gestor Funcionário. Por isso não existe um ator abstrato intermediário.

2Casos de uso · Visitante e Apoiador

O Apoiador generaliza o Visitante: tudo que é público permanece acessível depois de autenticado. O painel de transparência (UC08) é o único ponto do sistema que entrega dado financeiro sem exigir conta, o que materializa o objetivo de accountability.

Arraste na horizontal se a imagem estiver cortada.

3Casos de uso · Gestor

O Gestor Dono generaliza o Gestor Funcionário: faz tudo que o Funcionário faz e acrescenta quatro casos de uso exclusivos (UC16, UC18, UC19, UC20), que recebem ligação própria. UC16 e UC17 são as duas portas de entrada mutuamente excludentes — quem cria a instituição passa a ser Dono, quem solicita acesso passa a ser Funcionário — e ambas têm como pré-condição o gestor ainda não possuir vínculo aprovado (RF16, RN02).

Arraste na horizontal se a imagem estiver cortada.

Por que UC31 e UC32 são casos de uso separados. Atualizar o saldo é «include» porque acontece sempre que há movimentação (RF53); gerar alerta é «extend» porque acontece apenas na condição de o saldo cruzar a quantidade mínima (RF60, RN14). Essa distinção entre fluxo obrigatório e fluxo condicional é exatamente o que a banca procura em um diagrama de casos de uso.

4Como refazer os diagramas na ferramenta

Três caminhos, do mais recomendado ao mais rápido. Todos partem exatamente do mesmo modelo apresentado acima.

1. draw.io — recomendado

Abra app.diagrams.net e use Arquivo › Abrir de › Dispositivo para carregar o arquivo diagramas.drawio que acompanha esta página. Ele traz três abas: os dois diagramas de caso de uso e o modelo ER.

As formas usam notação UML nativa da ferramenta e as arestas estão conectadas às formas, não desenhadas por coordenada — arraste um caso de uso e as linhas se reposicionam sozinhas. Exporta em PNG, SVG ou PDF com fundo transparente, pelo menu Arquivo › Exportar como. É gratuito, roda no navegador e não exige conta.

2. PlantUML — se preferir manter o diagrama como código

Os dois blocos abaixo já vêm com tema aplicado e separados por grupo de atores, o que melhora bastante em relação ao diagrama único com os 40 casos de uso. Cole em plantuml.com/plantuml ou na extensão PlantUML do VS Code.

Ressalva honesta: mesmo assim o diagrama do Gestor continua mediano. O algoritmo de layout posiciona o ator fora do retângulo do sistema e traça linhas longas e curvas até os quatro pacotes. As alternativas de arranjo pioram: top to bottom direction gera uma imagem de 4091 × 724 px e, com linetype ortho, 3917 × 647 px — larguras inviáveis numa página A4. A versão mantida abaixo, de 1358 × 2528 px, é a de proporção mais aproveitável.

Se quiser mesmo permanecer no PlantUML com boa aparência, o caminho é gerar um diagrama por pacote: com seis a oito casos de uso cada, o layout se comporta bem. O custo é ocupar mais espaço no artigo.

3. dbdiagram.io — só para o modelo ER

Para o diagrama de entidades, esta é a melhor saída visual com menos esforço: cole o DBML da seção 7 em dbdiagram.io e o layout sai pronto, com as cardinalidades corretas e exportação em PNG, PDF ou SQL. Não serve para casos de uso.

Sobre o SVG desta página. Os diagramas exibidos acima também são arquivos vetoriais: clicando com o botão direito em cada um é possível salvar a imagem, e a página inteira imprime em PDF com os diagramas em qualidade de vetor. Serve se você quiser usar como está, sem passar por ferramenta nenhuma.

5Diagrama Entidade-Relacionamento

Dez entidades. As quatro fundações são usuarios, instituicoes, categorias e membros_instituicao — esta última é a tabela associativa que resolve o vínculo com papel e situação. Toda entidade transacional carrega instituicao_id, o que sustenta o isolamento exigido por RN05 e RNF16.

Linhas tracejadas indicam relacionamento opcional de origem (a doação que originou a entrada de estoque e o gestor que aprovou o vínculo). Cardinalidade completa na tabela abaixo.

// dbdiagram.io  /  dbml
Table usuarios {
  id int [pk, increment]
  nome varchar(100) [not null]
  email varchar(150) [not null, unique]
  senha_hash varchar(255) [not null]
  tipo_usuario tipo_usuario_enum [not null]
  telefone varchar(20)
  criado_em timestamp [not null]
  atualizado_em timestamp [not null]
}

Table instituicoes {
  id int [pk, increment]
  nome varchar(120) [not null, unique]
  cidade varchar(60)
  estado char(2)
  descricao text
  email_contato varchar(150)
  telefone varchar(20)
  site varchar(200)
  criado_em timestamp [not null]
}

Table categorias {
  id int [pk, increment]
  nome varchar(80) [not null]
  tipo categoria_tipo_enum [not null]
  instituicao_id int [null, note: 'nulo = categoria padrao do sistema']
  criado_em timestamp [not null]
  indexes { (nome, tipo, instituicao_id) [unique] }
}

Table membros_instituicao {
  id int [pk, increment]
  usuario_id int [not null]
  instituicao_id int [not null]
  papel papel_enum [not null]
  status status_membro_enum [not null, default: 'Pendente']
  data_solicitacao timestamp [not null]
  data_resposta timestamp [null]
  aprovado_por_id int [null]
  indexes { (usuario_id, instituicao_id) [unique] }
}

Table doacoes {
  id int [pk, increment]
  tipo tipo_doacao_enum [not null]
  valor decimal(12,2) [null]
  item varchar(120) [null]
  quantidade int [null]
  unidade varchar(20) [null]
  descricao text
  anonima boolean [not null, default: false]
  doador_id int [null, note: 'nulo quando doador externo']
  doador_nome varchar(120) [null]
  instituicao_id int [not null]
  categoria_id int [null]
  data_doacao timestamp [not null]
}

Table despesas {
  id int [pk, increment]
  numero_documento varchar(60) [not null]
  data_emissao date [not null]
  valor_total decimal(12,2) [not null]
  descricao text
  arquivo_url varchar(300) [null]
  categoria_id int [not null]
  instituicao_id int [not null]
  doacao_id int [null, note: 'RF44 - doacao que custeou']
  criado_em timestamp [not null]
}

Table itens_estoque {
  id int [pk, increment]
  nome varchar(120) [not null]
  descricao text
  unidade_medida varchar(20) [not null]
  qtd_atual int [not null, default: 0]
  qtd_minima int [not null, default: 5]
  preco_referencia decimal(12,2) [null]
  ativo boolean [not null, default: true]
  categoria_id int [not null]
  instituicao_id int [not null]
  criado_em timestamp [not null]
  atualizado_em timestamp [not null]
}

Table movimentacoes_estoque {
  id int [pk, increment]
  tipo tipo_mov_enum [not null]
  quantidade int [not null]
  observacao text
  data_mov timestamp [not null]
  item_id int [not null]
  gestor_id int [not null]
  doacao_id int [null, note: 'RF56 - entrada originada de doacao material']
}

Table alertas {
  id int [pk, increment]
  mensagem varchar(300) [not null]
  lido boolean [not null, default: false]
  criado_em timestamp [not null]
  item_id int [not null]
}

Table auditoria {
  id int [pk, increment]
  entidade varchar(60) [not null]

  operacao operacao_enum [not null]

9Decisões de modelagem que valem explicar no artigo

  • Gestor Dono generaliza Gestor Funcionário, sem ator abstrato. Como o Dono executa todos os casos de uso do Funcionário e acrescenta quatro, a relação entre eles é de superconjunto, e a generalização direta expressa exatamente isso. Um ator abstrato intermediário só se justificaria se cada um tivesse casos de uso que o outro não tem, o que não ocorre. Já UC16 e UC17 ficam com o ator que o executor passa a ser ao concluí-los — mesma lógica do ator Cliente executar “Cadastrar-se” sem ainda ser cliente. A restrição de que ambos só valem antes do vínculo é temporal, não de papel, e por isso aparece como pré-condição do caso de uso, não como um terceiro ator.
  • Vínculo como entidade, não como coluna. membros_instituicao existe porque o vínculo tem atributos próprios: papel, situação, data de solicitação, data de resposta e quem aprovou. Guardar instituicao_id direto em usuarios inviabilizaria o fluxo de aprovação (RF15, RF19) e o histórico de solicitações rejeitadas.
  • Saldo de estoque derivado, não digitado. itens_estoque.qtd_atual é um campo materializado por desempenho, mas a verdade está em movimentacoes_estoque (RN11). Por isso RNF30 exige que gravação da movimentação, atualização do saldo e geração do alerta ocorram na mesma transação — sem isso os dois valores divergem e a prestação de contas perde credibilidade.
  • Doador opcional em doacoes. O par doador_id nulo + doador_nome preenchido cobre a doação recebida fora do sistema (RF36), realidade de qualquer ONG pequena. O inverso, doador_id preenchido, habilita o histórico do apoiador (RF32).
  • doacao_id em despesas e em movimentações. São os dois elos que transformam registro isolado em rastreamento de aplicação de recurso (RF44 e RF56). É a principal diferença estrutural em relação ao sistema analisado, onde doação, despesa e estoque não se conversam.
  • categorias com tipo e instituição opcional. Uma única entidade atende receita, despesa e estoque (RF45, RF47). Com instituicao_id nulo a categoria é padrão do sistema; preenchido, é própria da organização. Evita três tabelas quase idênticas.
  • auditoria genérica. O par entidade + entidade_id registra qualquer operação de escrita sem criar uma tabela de histórico por entidade (RF81). Simples de implementar com um interceptador no SaveChanges do Entity Framework.
  • O que deliberadamente não está no modelo. Não há entidade de pagamento, de vaga de voluntariado nem de candidatura. A doação é declaratória e o voluntariado está fora do escopo (seção 2.10 do documento de requisitos) — vale dizer isso na defesa antes que perguntem.
